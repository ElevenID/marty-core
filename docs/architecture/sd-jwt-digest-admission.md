# SD-JWT digest selection and admission

Core uses the accepted private SD-JWT fork at
`ba5a9a154ae530ddcfcc5b52adf3da71e91b1929`. It supports SHA-256, SHA-384 and
SHA-512 disclosure hashes and key-binding `sd_hash`. These are separate from
the issuer and holder JWS signature algorithms.

## Existing entrypoints

Existing issuer preparation, remote batch construction, signature verification,
disclosure selection, wallet receipt and wallet presentation entrypoints retain
SHA-256. The fork update does not admit new algorithms in a product profile or
in the Python binding. The existing public request and policy structs remain
source-compatible.

Absent `_sd_alg` means SHA-256. Invalid types, unsupported names, noncanonical
case and duplicate JSON members fail; none selects a fallback algorithm.

## Explicit native use

An issuer profile can select `SdJwtDigestAlgorithm` through
`prepare_sd_jwt_with_options_and_digest_algorithm` or
`prepare_remote_sd_jwt_with_digest_algorithm`. A remote batch item can use
`RemoteSdJwtBatchItem::with_digest_algorithm` before it enters the existing
batch planner. All three paths still return opaque preparations for external
signing; they do not import a private key or perform local issuance signing.

The selected algorithm follows the immutable plan through disclosure encoding,
digest jobs, routing restoration and assembly. Returned digest lengths are
checked against each credential's algorithm. Serial execution remains the
default. The selector is signed at the top level, including non-default
algorithms on credentials with no disclosures so later key binding is clear.
Default SHA-256 bytes and source-consumption order remain unchanged.

A native verifier must explicitly admit the selected digest using
`verify_sd_jwt_with_policy_and_digest_algorithms`. The original issuer payload
is consulted after the fork authenticates it; configured issuer identity and
issuer/holder signature-role policies remain required. Core's additional
key-binding check uses that same algorithm over the original presented bytes.
An empty digest allowlist rejects the credential.

`create_sd_jwt_presentation_with_digest_algorithms` provides matching explicit
selection. Like the original selection helper, it does not establish issuer
authority or construct holder proof. An authenticated verifier and opaque
holder signer remain necessary for those operations.

## Qualification

The native unit cases cover both payload formats, disclosure-free credentials,
unchanged SHA-256 bytes, original encoded disclosure commitments, mixed digest
batch routing and rejection of a digest with another algorithm's length. The
maintained disposable OpenBao test
`explicit_sd_jwt_digests_bind_opaque_issuer_and_holder_signatures` exercises all
three algorithms with and without disclosures, non-exportable issuer/holder
keys, default admission and a genuinely signed KB-JWT with the wrong digest.

`sd_jwt_multi_digest` runs the same public-only signed vectors natively and in
the WASM runtime, checking explicit admission, issuer/signature policy,
original-byte selection and malformed/duplicate selectors. Its fixture can be
regenerated by the maintained OpenBao case with an explicitly supplied
`MARTY_TEST_SD_JWT_DIGEST_PUBLIC_FIXTURE` output path. The fixture contains only
synthetic public credentials and verification keys. It carries no private key
or live issuer authority and does not qualify a deployed product profile.
