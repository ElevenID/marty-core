# Wallet verifier request authentication

## Pre-registered clients

`wallet_request_auth::authenticate_registered_presentation_request` verifies the original compact JWS before producing consent fields. `WalletEngine::authenticate_registered_presentation_request` additionally retrieves that JWS through the existing bounded, public-address-only HTTPS transport. An invocation locator may contain only `client_id`, `request_uri` and optional `request_uri_method=get`; duplicate parameters and unsigned fallback fields are refused. A direct HTTPS request-object URL is also supported. JSON responses and unsigned request objects are refused.

This initial profile supports a pre-registered client ID without a colon, ES256, `oauth-authz-req+jwt`, exact registered `kid`, `direct_post`, and one `dc+sd-jwt` DCQL credential query with unique flat claim paths. Claim IDs are optional without `claim_sets`. Other query constraints, `client_metadata`, transaction data, legacy client-ID schemes, DID/certificate/federation/attestation profiles, Presentation Exchange and encrypted responses are refused. This is a deliberately bounded subset of [OID4VP Final](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html#section-5.9.2).

The adapter must acquire `RegisteredVerifierAuthority` from a fresh governed verifier relationship, scoped to its paired organization and trust profile. The governance owner must authorize the client, request-signing public key/key ID, exact response URIs, revision and validity interval. Issuer trust, an embedded JWK, the retrieval URL, or a publicly discoverable key is not that authority. This library neither creates those relationships nor supplies a governance endpoint.

The authenticated envelope retains the original JWS and authority identity/revision. Bind consent to those exact bytes. The asynchronous retrieval API reads the current clock both before and after its network await; a request or authority expiring during retrieval is refused. Before preparing or signing a presentation, obtain fresh governed authority, authenticate the request again at the current time, and require the approved signed request to remain unchanged. Expiration, revocation, changed authority or changed request requires refusal or a new consent journey. The envelope is not a persistent trust grant or holder-signing permission.

The historical `parse_presentation_request` API remains decoding-only and is explicitly documented as such. This additive API does not make its callers authenticated. Authenticator #57 still needs consumer wiring; issuer-key projection cannot be reused as verifier authority. Existing managed DID request production is outside this initial pre-registered profile.

## Governed DID clients

`WalletEngine::authenticate_governed_did_presentation_request` supports a separate, explicit `decentralized_identifier:` profile through `GovernedDidVerifierAuthority`. The caller must obtain a fresh governed verifier registration, not construct authority from a request-supplied key or public DID alone. `observed_at`/`expires_at` limit the governance snapshot to60seconds and remain separate from request-key validity. The original compact request, exact recipient, full client identifier, key ID, nonce, state and unsupported-semantics refusal are retained.

The engine resolves the DID method and compares its authentication key with the governed public ES256 key. `did:jwk` uses its canonical `#0` method; `did:key` uses its fingerprint fragment. `did:web` maps its identifier to the method-defined HTTPS location and uses the existing DNS-pinned public-address-only, redirect-free, proxy-free transport. It accepts bounded unique-member DID JSON, requires the exact document subject, method/controller and authentication relationship, and rejects ambiguous/embedded method definitions across verification relationships. JSON-LD contexts are refused rather than approximated. The supported `did:web` path profile uses unreserved ASCII path segments; encoded separators/traversal and IP-address authorities are refused. See [OID4VP client identifiers](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html#section-5.9.3), the [did:web resolution algorithm](https://w3c-ccg.github.io/did-method-web/#read-resolve), and [DID JSON representation](https://www.w3.org/TR/did-core/#json).

This bounded request profile supports one `dc+sd-jwt` query, unique flat claim paths, optional `meta.vct_values`, and signed client metadata advertising supported issuer/holder algorithms. Type and algorithm constraints remain in the authenticated envelope and are enforced by `verify_sd_jwt_for_consent` before credential selection. `prepare_sd_jwt_presentation` verifies the credential again, requires exactly the approved required claim set, and derives nonce/audience from that authenticated request. An unsupported holder algorithm, credential type or issuer algorithm fails before holder signing. Other formats advertised in metadata do not authorize choosing an unsupported query format. Encrypted responses, transaction data, legacy client-ID schemes, claim alternatives and unknown security-relevant fields remain unsupported and refused.

`consent_binding_digest` binds the original JWS and exact authority identity/revision. Before preparation, acquire fresh authority and call `reauthenticate_governed_did_signed_request` on the original approved bytes, then compare the consent binding. Do not refetch a newly signed replacement request during consent. Candidate verification and preparation also check both request and snapshot deadlines. The application still owns one-use session consumption, fresh governance/liveness checks before completion/submission, exact prepared-signature verification and delivery to the authenticated recipient; these APIs do not by themselves qualify a stored wallet or grant persistent signing permission.

The current registered-verifier owner projection does not yet supply this DID profile or its per-instance exact-recipient relationship. Those owner and paired-device contracts, native bridge generation and installed-wallet acceptance remain required. The API does not replace exact recipient registration with a wildcard or trust a service URL as issuer governance.

Native qualification includes method-mapping/document/key-binding tests and a guarded TLS OpenBao case that creates non-exportable verifier, issuer and holder keys, authenticates a DID request, mints a synthetic SD-JWT, enforces signed type/algorithm and complete claim selection, and verifies the final remote-signed holder proof's nonce and full client audience. The positive DID method in that fixture is self-certifying `did:jwk`; synthetic DID JSON tests are not a public-network `did:web` run. No installed-device, deployed-governance or official-suite result is implied.

Local qualification uses the normal verification-only wallet graph and the existing guarded disposable TLS OpenBao runner. `MARTY_TEST_WALLET_REQUEST_AUTH_ONLY=1 bash scripts/test_remote_issuer_live_kms.sh` runs the focused cases with non-exportable remote keys; the full hosted runner also includes them. These are library/transport contract and remote-signature fixture tests, not installed-wallet or external interoperability acceptance.
